# Nursing Schedule Management

The existing PHP/MySQL module now contains Monthly Duty Scheduling, Request-Off Management, Exchange of Duty, and Request Leave. Shared branding, navigation, account menu, light/dark theme and mobile controls are retained. No employee rows or published roster snapshots are migrated or replaced.

## Installation and configuration

Run `C:\xampp\php\php.exe database\install_nursing_schedule_management.php`. It performs additive, idempotent schema creation and verifies existing roster IDs, versions and final snapshots did not change. There are no example employee/request/roster records in the application database.

Super Admin opens the existing policy configuration page through Monthly Scheduling → Rest settings (`pages/schedule_configuration.php`) to configure reporting approvers, scheduling eligibility, fixed shifts, credited shift hours, operating days, operational shifts, holidays, leave eligibility/duration/document requirements, and leave credit hours. The actual `users.user_id` is the shared permanent account identifier; the existing `users.employee_id` is shown on forms. `user_departments` is reused when installed. No employee masterlist is duplicated.

The old authentication aliases merge Assistant Chief and Supervisor. `includes/nursing_approval.php` preserves their actual roles for the new request routes. Missing required independent approvers block submission with a configuration message. Configured hierarchy overrides the fallback same-unit Head Nurse / role-qualified nursing-wide superior candidates. A configured formal delegate must hold the required actual approval role. Super Admin cannot substitute for an approver.

Initial OPD/NSO/Nursing Training/CSSR policies use weekday operating days and default fixed shift 8. Supervisors, Assistant Chief and Chief use fixed daytime assignments even in a mixed clinical roster. Daytime defaults deduct one meal hour (6/7/8 credit eight hours, M credits ten); these are editable initial planning values and must be confirmed against hospital policy. Leave credits default to zero until configured and apply only to officially recorded attendance leave; manual planning codes do not establish official authorization. Holidays must be entered in the shared holiday calendar; no guessed Philippine holiday calendar is inserted. OR automation and finalization are blocked until its actual operational shifts are configured; configured OR operating days and shift choices are enforced.

## Scheduling

Monthly Duty Scheduling follows the latest approved user flow: automatic department roster loading and nine steps (Department, Month, Load Department Employees, Review Request-Off and Leave, Shift Type, Generate or Manual, Review, Hours Summary, Finalize). Back/Next scroll the existing panels and preserve the current state. Monthly Scheduling permits only the current and future months using the hospital timezone; past months/years and previous-month controls are disabled or removed. The API and monthly-save backend reject past periods. Stored histories and neighboring-month rest references remain intact for audit and validation. The sample's ten-section form, horizontal List View, Calendar View, summary cards, validation, legend and workflow actions are retained. All eligible active nursing employees in the selected department load automatically into new and editable monthly drafts from the central masterlist; nurses sort before attendants. Loading the department roster also hydrates approved Request-Off, internal leave indicators and actual neighboring-period shift definitions. The server rejects omitted eligible department employees on draft save or submission. Existing saved duties for transferred or inactive staff remain recorded; an inactive employee can be removed from an editable draft through a confirmation, while approved exchange duties stay protected. Published, approval and historical snapshots retain their existing membership. Inactive accounts, clerks, doctors and accounts disabled for scheduling are excluded. No duplicate masterlist or scheduling page is introduced.

Automatic Mode displays Generate Schedule; Manual Mode displays Open Manual Roster. Opening a manual roster or resetting a populated draft requires confirmation and clears editable duty entries while preserving protected exchanges and entered absences. The three cards report employees at the configured target (normally 176), required coverage gaps and prohibited PM-to-AM transitions. List, Calendar and Hours Summary are alternative views of the same state. Validate Schedule recalculates current conflicts; finalization runs authoritative backend validation.

The existing independent approval requirement remains: Finalize and Publish on a draft submits it for review, then a different authorized approver approves and publishes the version. The confirmation explains this distinction. Published status displays Finalized. PDF uses browser printing rather than a separate PDF service. These retained workflow/export behaviors are the remaining differences from a one-click interpretation of the sample.

Shift Master stores internal IDs, displayed labels, start, elapsed duration, meal deduction, credited hours and cross-midnight flag, with department overrides. Legacy internal IDs remain compatible; 12-hour DAY12/NIGHT12 display AM/PM and ADJUST8 displays AM8. PM8 is supported. Published JSON snapshots retain their shift definitions and revisions retain the original payload.

Fixed generation repeats configured employee shifts only on operating dates, preserving holidays, approved unavailability and locks; it reports target differences without adding weekend work. Rotating generation uses the existing browser MILP solver with mandatory rest, eligibility, exact-hour and coverage constraints. Soft per-employee shift-distribution penalties and previous-month counts improve fairness; nurses are considered before attendants for operational coverage. Custom credited-hour definitions use an exact hours constraint instead of assuming every duty credits eight or twelve hours. It is a proposal solver, not a proof that every mathematically feasible roster will be found. Unresolved deficits or operational coverage generate an infeasible result rather than silently weakening constraints. Exact targets, blank cells, duty pattern, current eligibility, overlap/rest, consecutive duties, rolling rest days, overnight approved absences, configured role-specific coverage and required operational shifts are checked server-side before submission, approval and publication.

Manual Calendar and horizontal List View share one payload. List supports sticky names/headers, touch/click editing, arrow keys, Enter, cell copying and pasted tab/newline blocks. Approved exchange cells are protected; locked cells survive regeneration. Manual cell edits and multi-cell pastes block prohibited transitions and insufficient rest before changing the state; pastes validate the complete proposed block. Blanks stay distinct from OFF. Manual historical references use a separate versioned table and cannot overwrite existing final rosters. Missing preceding-month records do not disable generation; warnings and reviewer acknowledgement are recorded before finalization.

The printed roster retains the dynamic duty legend, including descriptive leave/holiday definitions. Publication sends notifications through the existing notification table. PDF uses the browser's Print / Save as PDF facility. Excel export produces an XLSX workbook with a horizontal monthly roster, hours summary, and dynamic duty legend. Inline text cells prevent formula injection. Its package follows [Microsoft SpreadsheetML](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/structure-of-a-spreadsheetml-document). Scheduled working hours, configured leave credit hours and attendance-derived actual hours are separate. No actual-rendered-hour value is invented; it is shown as Not recorded because this application's attendance/leave integration does not supply that figure to the scheduler.

## Request workflows

Nursing Schedule Management has exactly four child modules: Monthly Duty Scheduling, Request-Off Management, Exchange of Duty and Request Leave. Both the general Nursing sidebar and the scheduling sidebar expose the existing routes as direct scheduling links without expandable scheduling submenus, preserving their role restrictions. Request history, pending approvals and Exchange pages remain accessible through the page tabs. Request-Off and Leave share an Off / Leave Application encoder with a Request Type dropdown containing OFF and every enabled leave policy category. The Request Type dropdown displays full names without code prefixes. Switching Request-Off/Leave updates the form in place without page navigation, preserving department, eligible applicant and entered reason; each kind retains its headings, histories and pending approval queues through the existing `nursing_requests.php?kind=OFF` and `kind=LEAVE` routes; their shared backend is reused without duplicate pages. Each module has a direct sidebar encoding link for eligible nursing employees and System Admin. System Admin selects Department first, then an eligible active employee from that department when encoding on their behalf. The Employee field stays disabled until a department is selected; switching departments clears the prior applicant and readonly details. The backend validates a posted department filter against the actual selected employee. Applicant identity, department, role, eligibility and approval route are resolved by the server; audit events record the actual administrator as encoder. The applicant stays fixed when resuming a draft or correcting a returned request. My Requests shows applications encoded by that administrator. System Admin may approve, reject or return requests at the current required approval stage; every required stage remains separate and records the actual administrator. Encoding does not grant withdrawal authority. Approval queues and decisions are restricted to Head Nurse, Supervisor Nurse, Assistant Chief Nurse, Chief Nurse and System Admin. Nursing approvers retain their assigned hierarchy and department scope; System Admin can act at any current required stage. Staff Nurses and Nursing Attendants cannot access approval queues or make approval decisions. Request-Off has one server-enforced approval stage and never adds Chief Nurse approval. Higher nursing positions see an explicit Request-Off-not-applicable message. Leave retains its approval tracker and printable Internal Leave Approval Form, with Chief Nurse role exemption and completion at APPROVED_FOR_HR_FILING; HR processing remains outside the application.

The request review step shows approved request availability and separate internally cleared leave indicators. The link opens the existing Request-Off form (or request history for roles that cannot apply), preserving the open monthly draft. Reload after saving to refresh approved requests. Internally cleared leave is labeled for HR filing outside the system, does not grant official leave authorization and does not deduct HR credits. Recorded official attendance leave remains authoritative for work restrictions.

`pages/nursing_requests.php?kind=OFF`: NA/Staff -> Head; Head -> Supervisor. One approval only. Higher nursing positions cannot submit Request-Off. Approval and roster accommodation are separate; publication records ACCOMMODATED or NOT_ACCOMMODATED and retains audit history. Request-Off dates use the multi-select calendar: mouse or touch dragging selects a contiguous date range, starting on a selected date clears that range, and keyboard/single-date selection remains supported. Selected dates are readonly and submitted through the existing validated date payload. Approved request-offs are loaded into setup and generation. If preferred OFF dates cannot be accommodated, the authorized scheduler records a dated accommodation review reason in the duty editor. This retains the request approval and records NOT_ACCOMMODATED upon publication; mandatory coverage/rest checks remain enforced. Owners may withdraw approved preferences before publication. Late approval records the existing published outcome without changing duties. The scheduler cannot forge Request-Off approval by changing a local status. Published periods direct employees to Exchange of Duty.

`pages/nursing_requests.php?kind=LEAVE`: NA/Staff -> Head -> Supervisor -> Chief; Head -> Supervisor -> Chief; Supervisor -> Assistant Chief -> Chief; Assistant Chief -> Chief; Chief has AUTOMATIC_ROLE_EXEMPTION and no invented approval/signature. Completion is APPROVED_FOR_HR_FILING, never official HR authorization. Internal clearance does not remove duties or become officially authorized leave; authoritative absences come from existing recorded attendance leave. Supporting PDF/JPEG/PNG files (5 MB max) are stored behind Apache denial and served only after ownership, assigned-review or System Admin authorization. Document policy is enforced before ordinary approvals. Corrected applications restart approval rounds; rejection/return require remarks.

Exchange retains its atomic versioned application, partner consent, reservations, rollback handling and audit history. Higher positions start at the relevant superior. Cross-unit swaps require both employees to already be eligible members of the destination published rosters, matching nurse/attendant qualifications and review by both affected unit heads where applicable. No implicit cross-unit qualification or unilateral coverage arrangement is created. Duty Coverage remains unavailable because no such authorization/configuration existed in this application. The final Chief approval remains independent of both participants.

All request decisions and scheduling writes use current database identities, CSRF, scope/ownership checks, record versions and a shared transaction mutex. Request events and schedule revisions are append-only through application endpoints. DB administrators are outside the application's tamper-protection boundary. Existing `nursing_document_notifications` delivers request and schedule notices.

## Reconstruction additions and verification

Request-Off now has a multi-date calendar, optional remarks, persisted DRAFT records, resume/submit and single-stage approval. Leave includes start/end dates, server-validated inclusive duration and a supporting-document field at application submission. Documents are stored privately with owner authorization, MIME/size validation, a shared transaction mutex and upload audit events. Super Admin remains review/configuration-only; request identity comes from the actual nursing account.

Changed sources: pages/schedule_management.php, pages/nursing_requests.php, api/schedule_management.php, includes/schedule_management.php, includes/nursing_requests.php, public/js/schedule-management.js, public/js/schedule-engine.js, public/js/schedule-worker.js, public/css/nursing-requests.css, plus the existing request/schedule regression fixtures. Shared four-module navigation remains in includes/schedule_sidebar.php and includes/nursing_sidebar.php.

New test: tests/nursing-document-upload.test.cjs exercises actual HTTP multipart upload, private storage, ownership, MIME rejection and audit records against a disposable database. Request/workflow integration checks cover draft submission, month validation, internal leave indicators, publication notifications and concurrent approvals. Browser checks cover all four child routes, nine steps, central selection, calendar date selection, leave range/duration, manual PM-to-AM rejection, editing, exports, mobile drawer and light/dark layouts. Existing engine, storage, exchange and XLSX tests remain part of verification.

No historical records are deleted or rewritten. This reconstruction adds behavior to existing schemas; the existing additive installer remains available if schemas have not yet been installed. Basic one-qualified-nurse shift coverage is not a staffing adequacy assessment. The bounded proposal solver may report infeasibility without proving that every possible roster has been searched. Actual rendered hours remain Not recorded when attendance data does not supply that figure. PDF uses browser Save as PDF. OR operating requirements, paid-hour/meal definitions, holidays, reporting approvers and leave policies require hospital configuration before use.

Leave limits supplied by the user: Wellness Leave permits 5 days per calendar year with no more than 3 consecutive days; Force Leave (FL) permits 5 days per calendar year with at most 5 consecutive days; SPL permits 3 days per calendar year. Known consecutive limits are checked across adjacent pending and internally cleared applications on submission and approval, without modifying historical requests. FL is available in the shared encoder and schedule legend/absence handling. The confirmed calendar-year allowances are 5 WL, 5 FL and 3 SPL days per employee. Submission and approval enforce these allowances using unique dates across pending requests, internally cleared applications and recorded official attendance leave; rejected, withdrawn and returned applications do not reserve the allowance. Each year has a separate allowance, and overlapping records count a date once. These checks do not deduct HR leave credits or add an HR processing stage.

Employee Documents shows only fully internally approved leave applications and approval statuses in Attendance & Leave and employee profiles, limited to the existing authorized employee scope. Only the transition to APPROVED_FOR_HR_FILING records the actual final approver (or exempt applicant/encoder) and applicant in the document audit history. Pending, returned, rejected and withdrawn requests stay in Request Leave and its approval history. Yearly allowance validation includes manually encoded employee leave summaries without counting matching detailed attendance twice. Exhausted allowances reject new filing before a request is inserted, including attempts using dates already reserved.

Leave applications use the same clickable, mouse/touch drag-select calendar as Request-Off. Consecutive dates display as MM-DD-YYYY ranges with a live requested-day total. Leave month navigation preserves selected dates across months; OFF remains a single-month preference. Actual ISO dates are submitted through the existing shared request validation and annual/consecutive limits.
